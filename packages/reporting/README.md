# Aggregate product reporting

`materializeDaily(db, date, asOf)` is worker/server-only. It writes UTC date counts plus a complete-date watermark in one transaction. The worker initially refreshes 90 complete dates for mature-cohort prior-period comparison, then 45 dates for day30 cohort maturation and 14 further days of late telemetry. Delivery/bounce/complaint/open/click rates use acceptance-date message cohorts; coverage uses nonempty digest intents and accepted intents from the same scheduled-date cohort, never accepted-date totals divided by scheduled-date totals.

`recordAccountState` in the database package records full authoritative post-mutation snapshots inside the account mutation transaction. Only cohorts with a `verified_signup` baseline exactly at verification are measured. Existing users without baseline are unmeasured rather than retroactively reconstructed. Activation means three simultaneous monitors within seven days; retention means consented, enabled and unsuppressed with a monitor at day30. State sequence breaks timestamp ties. Historical data must remain complete for valid results; deletion/anonymization policy and engaged retention remain launch gates.

`readSummary` only selects `analytics_daily_aggregates`; it has no arbitrary SQL, table, account or recipient selector. Its API accepts dates (max92day span), allowlisted metric and bounded pagination only. Daily cells below10 are omitted. Period counters sum the complete requested UTC dates before the threshold is applied, allowing 3 daily signups to become a reportable monthly count. Missing/partial dates fail the matching watermark check and are unavailable, never zero. AI rates require visible numerator and denominator counts of at least10. No raw personal data is returned. Reported opens are unreliable estimates; clicks can be scanners.

`GET /api/admin/analytics/summary` requires a separate high-entropy `ANALYTICS_REPORT_TOKEN` of at least32characters. The bearer comparison is constant-time for equal lengths. Rate limits30authorized requests/minute in each process and logs only action/outcome; no authorization values, URLs or query text. Add edge/global limits before scaling beyond one web process. It returns no-store responses. Missing secret denies access; missing database returns503. Configure a read-only database role limited to aggregate SELECT for stronger runtime isolation before production.

`/admin` separately requires a current authenticated admin role; it never accepts the service bearer as a user login. It uses the internal `readOwnerSummary` aggregate-only helper to show rolling7/30day periods and adjacent prior comparisons from 90 complete dates. Owner counts may include small/zero cells; rates still require complete pairs with denominator>=10. The HTTP API has no owner/audience override. AI rates cannot infer suppressed zero numerators. Percentage-point change is available only when both matching rates exist. PostHog acquisition and engaged retention remain unavailable until configured; no fictional zero values. Metrics do not declare PMF or activate advertising.

Rolling activation rates use signup dates shifted seven days earlier than the displayed maturity-date window; retention shifts signup dates thirty days earlier. Prior periods use the identical shift. This compares cohorts that have fully matured, not recent immature signups against an older mature population. Every paired signup-date watermark must have been computed after that entire signup day matured. Responses show exact signup/cohort dates, reporting-window dates, maturity lag, computation timestamp range and visible numerator/denominator counts. Requested ranges too short to include shifted dates yield unavailable rates/comparisons. Calendar flow counts remain unshifted. Standalone explicit-date period rates describe the matured subset of the requested signup dates rather than silently querying outside that range.

Explicit `unsubscribe_completed` and `digest_consent_withdrawn` events identify distinct accounts withdrawing within each UTC day. The rate denominator is observed verified accounts that were consented, enabled and unsuppressed at any point during that day; the numerator is withdrawals among that same at-risk cohort. Multiday totals are account-days, not lifetime-unique subscribers. Provider `email_bounced` and `email_complained` events are separate. Legacy generic `suppressed` events are counted as unclassified and never silently relabelled unsubscribe.

`materializeSourceSnapshot(db, observedAt)` records current observed source gauges on the observation's UTC date only. The worker must pass its current clock; do not backfill prior source health from today's mutable rows. Fresh means success within four hours. Failing means failureCount>0; a history-coverage warning is not a fetch failure. Disabled/paused or removed mappings are excluded from enabled-source rates. Rolling source counts/rates use the latest complete snapshot in each period, not the sum of daily gauges. Unknown snapshots remain unavailable.

Production Neon migrations, real provider metrics and owner reporting access remain unaccepted.

These cover shifted mature cohorts, missing-watermark rejection, zero/low-count owner separation, explicit withdrawal taxonomy, observed-only source gauges and scheduled-versus-accepted date cohorts. Consolidated root validation, current-image acceptance and real PostHog ingestion/MCP queries are separate gates.
